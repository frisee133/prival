### Временная ссылка без VPN

На подготовленном компьютере получить текущий публичный адрес или запустить новую пару туннелей можно в PowerShell из каталога проекта.

```powershell
& ".\scripts\temporary-link.ps1"
```

Скрипт проверен в Windows PowerShell 5.1 и PowerShell 7. В файлах PowerShell сохранён UTF-8 с BOM, консоль и native-вывод используют UTF-8. Каждый вызов Pinggy ограничен 35 секундами, stdout и stderr пишутся в отдельные .local/pinggy-*.log. При тайм-ауте выводится путь к журналу. После проверки страницы и API публичный адрес печатается последней строкой. Повторный запуск использует действующие туннели. При обновлении локального сертификата TURN проверка перезапускает LiveKit, чтобы он прочитал новый файл. На этом Windows-стенде для медиа используется UDP-диапазон 17900–18000: в повторной проверке TURN с одиночным UDP mux не получал ответов ICE, а выделенный диапазон восстановил передачу.

Последняя строка команды — адрес для друга. Оставьте компьютер и службы включёнными. В приложении кнопка **Пригласить по ссылке** добавит к адресу код отправителя. Новый пользователь вводит ник и подтверждает предзаполненную заявку. Получатель не получает права владельца. Бесплатная сессия Pinggy ограничена 60 минутами. По истечении срока повторите команду и отправьте свежую ссылку. При смене домена ключ прежнего браузерного профиля остаётся привязан к старому адресу. Для сохранения дружбы между сессиями используйте стабильный адрес. [Условия временных туннелей](https://pinggy.io/help/)

Веб и сигналинг проходят через публичный HTTPS/WSS-туннель к выделенному HTTP-шлюзу на 127.0.0.1:18880. Для медиа открыт второй исходящий туннель, который выдаёт отдельный публичный TCP-порт. На этом адресе клиенты используют TURN/TCP с краткоживущими учётными данными. Мост на 127.0.0.1:19444 доставляет трафик на локальный TURN/TLS с проверкой его сертификата. WebRTC шифрует аудио между клиентом и SFU. В сетях, где разрешён только исходящий TCP 443, этот публичный тестовый медиапорт может быть недоступен. Для таких сетей используйте публичную конфигурацию с TURN/TLS на 443 или проверенный частный маршрут.

Для VPN передайте другу **только** файл `.local/Привал-VPN-CA.crt` с публичным корневым сертификатом. Сравните SHA-256 файла по независимому каналу. На подготовленном стенде он равен `1FB181B2867E1031369A088871A52E6920F05562EFECE0FBA5D0E8EACD1DB833`. Ключи из `.local/private-ca` остаются у владельца. Для Edge/Chrome в Windows друг может доверить проверенный сертификат текущему пользователю следующей командой в каталоге с полученным файлом. Это даёт доверие сертификатам данного центра в профиле Windows.

```powershell
Get-FileHash -Algorithm SHA256 '.\Привал-VPN-CA.crt'
certutil -user -addstore Root ".\Привал-VPN-CA.crt"
```

Оба участника подключаются к одной сети Radmin и открывают VPN-ссылку. Создайте профили, обменяйтесь кодами, нажмите **Добавить друга**, затем **Заявки → Принять заявку**. В разделе **Друзья** нажмите **Позвонить**, на другом ПК — **Принять звонок**. Для обычной речи включите микрофоны. Другу с доступом к публичной установке достаточно современного браузера.

После перезагрузки подготовленного компьютера запустите из рабочей папки:

```powershell
& ".\.local\Запустить.ps1"
```

Скрипт запускает PostgreSQL, API, SFU и локальный сигналинг. При наличии настроенного адреса Radmin он также запускает HTTPS-шлюз. Локальный Windows-клиент находится в `dist/windows/Привал/Привал.exe`; переносите всю папку вместе с EXE. Для другого сервера задайте его адрес в `server.json` рядом с программой. Ключ Windows-профиля и ключ обычного браузера независимы.

## Почему прежняя ссылка не работала

Сайт и API слушали 127.0.0.1:18080, а прокси сигналинга — 127.0.0.1:17880. Проверка страницы и `/api/health` возвращала HTTP 200 на loopback. Обе попытки через Ethernet-адрес этого же ПК 192.168.1.100 завершались без HTTP-ответа. Адрес 127.0.0.1 в браузере друга указывал бы на компьютер друга. На стадии загрузки страницы проверять права или микрофон ещё рано.

Теперь шлюз слушает адрес Radmin на TCP 18443 и обслуживает страницу, относительный `/api` и WebSocket на одном HTTPS-адресе. API выбирает адрес WSS по разрешённому Origin, LiveKit объявляет VPN-адрес для медиа. Диагностика на самом узле дала HTTP 200 для страницы и API после проверки TLS-цепочки, HTTP 403 для сигналинга без JWT. Два браузера на этом ПК подключились через VPN-адрес и обменялись разными аудиотонами. Профиль Windows Firewall для Radmin — Public. Есть входящие разрешения на точные пути к нативным Caddy и LiveKit. Для этого стенда нужны TCP 18443, ICE/TCP 17882, ICE/UDP 17900–18000 и резервный TURN/TLS на 443/tcp.

Публичный адрес Pinggy проверен независимыми HTTP-узлами. Главная страница вернула HTTP 200 из Германии, Ирана и Казахстана; отдельная проверка /api/health из Тегерана также вернула 200. [Страница](https://check-host.net/check-report/578a9ae3k412) · [API](https://check-host.net/check-report/578a9945kb1c). Эти проверки подтверждают достижимость через интернет. Голосовые клиенты находились на одном ПК. Мобильная сеть, второй физический компьютер и панель домашнего роутера в тесте не участвовали. Маршрутизатор не ответил на локальный запрос UPnP IGD. WAN-адрес и правила проброса не подтверждены, наличие CGNAT не установлено. При домашней публикации сравните WAN-адрес в роутере с публичным адресом, проверьте входящий трафик с мобильного интернета. Если WAN приватный или из 100.64.0.0/10, а публичный адрес другой, вероятен дополнительный NAT. Для обычной ссылки подойдёт Linux-хост с публичными адресами либо доступный извне домашний сервер с DNS и пробросом портов. HTTP-туннель сам по себе не доставляет ICE/UDP и TURN-трафик.

## Профиль и полномочия

Регистрация открыта. Ник может повторяться. Сервер назначает отдельный UUID и случайный код для обмена заявками. Регистрация создаёт роль участника. Пользователь добавляется только после принятия заявки. Владелец отдельно назначается серверной командой по коду уже созданного профиля и получает доступ к статистике сервера.

Браузер генерирует Ed25519 через Web Crypto и сохраняет закрытый неэкспортируемый CryptoKey в IndexedDB. Для входа он подписывает одноразовый запрос, привязанный к сайту и операции. Запрос действителен 60 секунд. Завершённая регистрация и вход создают HttpOnly-сессию. В production включены Secure, SameSite=Strict и точная проверка Origin. Windows-клиент шифрует локальный ключ через Electron safeStorage с Windows DPAPI. [Web Crypto](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/generateKey) · [Хранение в Electron](https://www.electronjs.org/docs/latest/api/safe-storage)

**Удалить профиль** завершает участие в разговорах и удаляет серверную запись, сессии, дружбу, заявки и блокировки. Клиент очищает свой ключ и настройки после подтверждения сервера. При потере соединения он сохраняет намерение удалить профиль для повтора. Если очистить данные сайта вручную, ключ теряется. Следующая регистрация с тем же ником получит новый ID. Серверная запись старого профиля очищается по `PROFILE_RETENTION_DAYS`, по умолчанию через 180 дней неактивности.

Активный разговор хранится во временных строках БД. После окончания они удаляются, при исчезновении клиентов действует тайм-аут. История звонков и аудиозаписи не ведутся. Постоянных каналов и чата в версии с друзьями нет. Старые данные первой версии остаются в исходной БД, новые профили используют отдельные таблицы. Старый аккаунт владельца не превращается автоматически в ключ какого-либо посетителя.

## Установка с Docker Compose

Нужны Docker с Compose 2.24.4+ и Node.js 24.12+ для генератора секретов. Из каталога проекта:

```sh
node scripts/setup.mjs
docker compose up -d --build
docker compose ps
```

Откройте [локальный сайт Compose](http://localhost:3000), создайте свой профиль и скопируйте его код. Команда назначения владельца:

```sh
docker compose exec app node dist/server/cli.js owner КОД_ПРОФИЛЯ
```

Для подготовленной нативной сборки эквивалент — `node --env-file=.local/preview.env dist/server/cli.js owner КОД_ПРОФИЛЯ`. Только один профиль может владеть сервером. При удалении владельца новый назначается той же командой. Миграции запускаются автоматически под блокировкой PostgreSQL. `docker compose down` сохраняет том с БД.

## Публичный HTTPS, WSS и TURN

Готовая Linux-конфигурация использует два публичных IPv4, чтобы и веб, и встроенный TURN/TLS слушали TCP 443. A-записи веба и сигналинга указывают на первый IP, A-запись TURN — на второй. Адреса ниже — примеры. На одном IP для двух служб на 443 потребуется L4-маршрутизация по SNI.

```dotenv
APP_ORIGIN=https://camp.example.org
LIVEKIT_PUBLIC_URL=wss://voice.example.org
WEB_DOMAIN=camp.example.org
VOICE_DOMAIN=voice.example.org
TURN_DOMAIN=turn.example.org
WEB_BIND_IP=192.0.2.10
TURN_BIND_IP=192.0.2.11
MEDIA_IP=192.0.2.10
```

`WEB_BIND_IP` и `TURN_BIND_IP` должны быть адресами интерфейсов хоста; `MEDIA_IP` — достижимый клиентами ICE-адрес. Для домашнего NAT настройте соответствующий проброс. `APP_EXTRA_ORIGINS` позволяет нативной установке явно добавить HTTPS-адрес VPN-шлюза, который проксирует и сайт, и сигналинг. Внешний клиент получает WSS этого шлюза. Статические файлы обращаются к API по относительному пути.

Для TURN поместите сертификат с SAN для TURN-домена и его ключ в `deploy/turn-tls/fullchain.pem` и `privkey.pem`. Используйте публично доверенную цепочку, например ACME DNS-01. После обновления перезапустите LiveKit. Сертификаты веба и сигналинга получает Caddy. Откройте порты у провайдера и в firewall Linux, затем запустите:

```sh
docker compose -f compose.yaml -f compose.public.yaml config --quiet
docker compose -f compose.yaml -f compose.public.yaml up -d --build
```

| Назначение | Порт | Трафик |
| --- | --- | --- |
| Веб-IP | 80/tcp | ACME и переход на HTTPS |
| Веб-IP | 443/tcp | Приложение, API, WSS сигналинга |
| Веб-IP / MEDIA_IP | 7882/udp, 7881/tcp | ICE UDP mux и прямой ICE/TCP |
| Веб-IP / MEDIA_IP | 3478/udp | TURN/UDP, для которого LiveKit объявляет node_ip |
| TURN-IP | 443/tcp | TURN/TLS |
| Внутри Compose | 5432, 3000, 7880/tcp | PostgreSQL, Fastify, LiveKit RoomService и сигналинг |

Внешняя ссылка для друга — значение `APP_ORIGIN`. Для голосового входа Fastify выдаёт JWT на одну временную комнату, разрешает только microphone и проверяет сессию. Перед подключением Caddy запрашивает у API проверку текущего участия. Периодическая сверка завершает уже открытые соединения после удаления участника. [Порты LiveKit](https://docs.livekit.io/transport/self-hosting/ports-firewall/) · [Жизненный цикл JWT](https://docs.livekit.io/frontends/reference/tokens-grants/)

## Проверить связь с другого ПК

1. Откройте ссылку с мобильного интернета для публичной установки или с другого участника общей VPN. Проверьте доверие к сертификату, загрузку страницы, затем `/api/health`. Если страница не открывается, проверьте DNS A/AAAA, маршрутизацию, доступность порта и цепочку сертификата. Если открылась только страница, смотрите запросы `/api/device/challenge` и `/api/device/prove` через Network.
2. Создайте профиль, перезагрузите страницу, сверьте код. В двух разных профилях примите заявку, войдите в звонок и по очереди произнесите разные фразы. Проверьте ответы на получение токена и WebSocket 101. При одностороннем звуке проверьте захват и исходящий RTP у говорящего, входящий RTP, громкость и устройство вывода у слушателя.
3. В **Настройки звука → Статистика соединения** смотрите ICE-пару, RTT, джиттер и потери на входящих треках. В `chrome://webrtc-internals` сопоставьте transport.selectedCandidatePairId с localCandidateId и remoteCandidateId. Проверьте реальный адрес SFU. При блокировке воспроизведения нажмите **Включить звук**.
4. Для публичного TURN/TLS перекройте на тестовом клиенте прямой UDP и TCP 7881 к серверу. Оставьте DNS и TCP 443 к веб-IP и TURN-IP. Начните новый звонок. Проверьте тип relay, TLS/TCP и URL TURN на 443 в статистике. Проверьте звук в обе стороны и верните правила. Результат этого испытания из внешней сети пока не получен.

## Звук и Windows-клиент

В **Настройках звука** есть ползунок **Громкость микрофона** от 0 до 300%. 100% соответствует исходному уровню. Он меняет исходящий сигнал, который слышат собеседники. Если тихо слышно друга, усиление настраивает друг у своего микрофона. Изменение громкости применяется к активному звонку и локальному прослушиванию без повторного захвата устройства. Настройка сохраняется в том же браузерном профиле.

RNNoise и GTCRN заменены на **DeepFilterNet3** через `@workadventure/noise-suppression` 0.2.0; сохранён лёгкий WebRTC и режим без обработки. Старые настройки RNNoise/GTCRN автоматически выбирают DFN3. WASM, модель и AudioWorklet раздаются с самого сервера, внешнего облачного API нет. Захват — моно 48 кГц; у DFN3 браузерные `autoGainControl` и `noiseSuppression` выключены, настройка автоуровня включает обработку после модели. [API и параметры пакета](https://github.com/workadventure/noise-suppression#deepfilternet3).

Цепочка: микрофон → DFN3 с пауза-гейтом/look-ahead 30 мс → дополнительный VAD при его выборе (look-ahead 20 мс, удержание 250 мс, затухание 30 мс) → усиление → компрессор → конечный mute/PTT → MediaStreamDestination → LiveKit. DFN3 продолжает работать при отпущенной PTT; отключение передачи происходит после модели. Отпускание клавиши, deafen и выход закрывают передачу немедленно; задержка VAD не продлевает PTT.

На временном реле был воспроизведён обрыв больших ответов около конца файла (`ERR_CONTENT_LENGTH_MISMATCH`), хотя маленькие страница/API и звонки проходили. Для доменов Pinggy бинарные ресурсы загружаются проверяемыми HTTP Range-частями по 256 КиБ, с четырьмя параллельными запросами и ограниченными повторами. WASM предварительно сжимается при сборке (14,6 → 4,0 МБ), модель сохраняется в исходном gzip. Скомпилированная модель и адреса ресурсов кэшируются в текущей вкладке. На обычном сервере используется стандартный загрузчик пакета. CDN для моделей не требуется.

При устойчивой перегрузке модели (две 2-секундные выборки выше 70% доступного времени) или отказе загрузки включается WebRTC: прежний захват освобождается, создаётся новый с включённым системным шумодавом, обработанный выходной трек и состояние PTT сохраняются. В интерфейсе показана причина. Есть ручной выбор лёгкого режима; отслеживание перегрузки модели не заменяет измерение FPS в игре. Инициализация ограничена тайм-аутом, отмена закрывает устройство и поздно загрузившийся процессор. Усиление применяется после подавления шума и порога активации голосом. Компрессор смягчает громкие пики. У собеседников сохраняется индивидуальная громкость. При локальном прослушивании передача в звонок приостанавливается, при выходе освобождаются устройство и обработка.

Передача включается вручную, удержанием настраиваемой клавиши или порогом активации голосом. В браузере PTT требует фокуса вкладки. В Windows-клиенте выделенный обработчик Win32 Raw Input получает нажатие и отпускание выбранной клавиши при скрытом окне. В разговоре PTT заранее готовит аудиотракт с закрытым выходом. За пределами разговора и теста аудиоустройство освобождается.

```sh
npm ci
npm run typecheck
npm run build
npm test
npm run test:audio
npm run windows:build
```

Последняя команда выполняется на Windows с .NET Framework 4.x. Сервер раздаёт общий веб-интерфейс обоим клиентам.

## Windows-оверлей

Запустите `dist/windows/Привал/Привал.exe` и откройте **Настройки звука → Игровой оверлей**. Включите **Показывать оверлей во время звонка**, выберите угол и монитор. Вариант «Экран с указателем мыши» размещает виджет на экране указателя при обновлении состояния. Если выбранный монитор отключён, используется доступный экран.

Оверлей показывает участников разговора, подсвечивает говорящих и отображает состояние вашего микрофона. Он появляется во время звонка и работает при скрытом в трей основном окне. Мышь проходит в нижележащие окна, фокус остаётся у приложения пользователя. Настройки сохраняются на устройстве. После завершения разговора или удаления профиля виджет скрывается, при удалении профиля его настройки очищаются.

Проверены реальные события речи и PTT, сохранение положения, признаки always-on-top и WS_EX_TRANSPARENT в Windows, скрытие основного окна и удаление профиля. Сквозной ручной щелчок, исключительный полноэкранный режим конкретных игр и влияние на FPS ещё требуют игрового прогона. Для обычных окон и оконного полноэкранного режима используется отдельное прозрачное окно поверх рабочего стола.

## Проверки этой версии

На Windows с PostgreSQL, LiveKit 1.13.11 и Caddy 2.10.2 запущены интеграционные проверки. Синтетические микрофоны передавали разные PCM-тоны через настоящий WebRTC. Частота измерялась после декодирования воспроизводимого HTMLAudioElement.

| Проверка | Результат |
| --- | --- |
| Chrome на loopback | Два независимых клиента, один ник, разные UUID. Автовход после перезагрузки, неэкспортируемый приватный CryptoKey, дружба, звонок. Один получатель воспроизвёл 440 Гц, другой — 880 Гц |
| Chrome на HTTPS-адресе VPN | Та же проверка с двумя браузерами на одном компьютере. Для автоматизации закреплён публичный ключ сертификата. Отдельный HTTP-клиент проверил цепочку локальным CA |
| Публичная тестовая ссылка | Два Chrome на одном ПК открыли настоящий внешний адрес Pinggy, создали отдельные профили и обменялись звуком через внешний TURN/TCP. Для входящего аудио с обеих сторон наблюдался выбранный relay. В замере RTT составлял 182–231 мс. Публичный API прошёл тест прав, заявок, групповых звонков и удаления |
| TURN/TLS через VPN-адрес | В обоих клиентах были разрешены только relay-кандидаты с turns на TCP 443. На принятых аудиопотоках проверены relayProtocol=tls и фактическое воспроизведение 440 и 880 Гц |
| Разные способы удаления | Кнопка удалила дружбу и активный звонок у второго клиента. Очистка данных сайта позволила зарегистрировать тот же ник с другим ID и пустым списком друзей |
| Усиление и шумоподавление | Ранее регулировка 25 → 100% увеличила амплитуду у собеседника в 4,10 раза. После замены на DFN3 браузерный тест реального WASM снизил RMS синтетического шума с 0,0592 до 0,0007; подтверждены запрет передачи при закрытом PTT и работа модели в это время. Оценка разборчивости реальной речи ещё предстоит |
| API | Повторно использованная подпись и чужой Origin отклонены. Проверены роли, привилегированный запрос владельца, заявка, DND, групповой разговор, запрет второго одновременного звонка, блокировка |
| Windows | Подтверждение DPAPI-профиля после перезагрузки окна, голос в обе стороны. При скрытом в трей клиенте системное нажатие F8 передало тон собеседнику, после отпускания измерена тишина |
| Windows-оверлей | В исходной и собранной Windows-версии проверены подсветка говорящих, состояние микрофона, положение, отсутствие фокуса и Win32 WS_EX_TRANSPARENT. При скрытом основном окне PTT передавал тон, отпускание останавливало передачу. Игровой прогон пока не выполнен |
| Внешняя сеть и оборудование | Другой физический компьютер, голос через мобильный интернет, публичный TURN/TLS на 443 и реальная гарнитура пока не проверялись |

Воспроизведение интеграционных тестов требует работающего тестового сервера и Chrome. Они создают временные учётные записи и могут оставить старую запись при имитации очистки браузера.

```powershell
$env:TEST_ORIGIN='http://127.0.0.1:18080'
npm run test:api
npm run test:browser
$env:TEST_DESKTOP='1'
npm run test:browser
```

Для проверки тихой речи, клавиатуры, вентилятора и колонок повторите одну и ту же фразу на той же дистанции для каждого режима шумоподавления. Слушатель отмечает разборчивость, обрезание первого слога, остаточный шум и эхо. Физическое сравнение и объективная оценка качества голоса на этом стенде ещё не проводились.

Для сравнения в игре стенд — AMD Ryzen 5 5500, GeForce GTX 1660 SUPER, 16 ГБ ОЗУ. В Counter-Strike 2 используйте один демофайл, одинаковые графические настройки и трёхминутный отрезок. Повторите по три раза с закрытым приложением, в трее без звонка, в звонке с WebRTC и с DFN3. Измерьте средний и 99-й перцентиль времени кадра, CPU и суммарную память процессов клиента. Проверьте первый слог и отпускание PTT при фокусе игры. Игровой прогон и влияние на FPS пока не измерены.

Ранее отдельный нагрузочный прогон этого SFU с тремя синтетическими источниками и 17 слушателями дал 51/51 подписки, ноль потерь на loopback, 16% одного ядра и 107,9 МиБ памяти; входящий/исходящий RTP — 12,6/166,0 кБ/с. Это измерение SFU предыдущего этапа. Для повторения на отдельном стенде используйте `lk load-test --room benchmark --audio-publishers 3 --subscribers 17 --duration 75s` с секретами стенда в окружении. [Методика LiveKit](https://docs.livekit.io/transport/self-hosting/benchmark/)


## Что осталось после настройки звука

1. Финальная приёмка на двух физических ПК из разных сетей с реальными гарнитурами, включая тихую речь, шум клавиатуры, вентилятора и работу с колонками. Игровой прогон Windows-клиента должен сравнить время кадров, CPU и память.
2. Стабильная публикация для повседневного использования. Текущая временная ссылка меняет адрес после завершения сессии поставщика.

## Копия базы

```sh
docker compose exec -T db pg_dump -U prival -d prival -Fc -f /tmp/prival.dump
docker compose cp db:/tmp/prival.dump ./prival.dump
docker compose exec -T db rm /tmp/prival.dump
docker compose cp ./prival.dump db:/tmp/restore.dump
docker compose exec -T db createdb -U prival prival_restore
docker compose exec -T db pg_restore -U prival -d prival_restore --exit-on-error --single-transaction /tmp/restore.dump
docker compose exec -T db psql -U prival -d prival_restore -c "SELECT count(*) FROM profiles"
docker compose exec -T db rm /tmp/restore.dump
```

Для аварийного запуска переключите API на восстановленную БД и примените миграции. Храните отдельно серверный `.env`, сертификаты и том Caddy. Закрытые ключи пользовательских профилей в архив БД не входят.
